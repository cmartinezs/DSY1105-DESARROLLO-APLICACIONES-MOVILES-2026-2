# Banco de dinámicas vivas · DSY1105

Este banco reúne actividades breves y reutilizables para mantener activa la asignatura sin desviar el foco de Kotlin, Android y PocketLog. La regla es **rotar pocas dinámicas y reutilizarlas con contenidos distintos**.

## Regla operativa

Por semana se recomienda escoger **1 dinámica principal** y, como máximo, una segunda muy breve. Deben usar contenido ya trabajado o correspondiente a la semana actual.

## Dinámicas disponibles

### Java vs Kotlin duel · 10–20 min
Resolver o leer la misma intención en ambos lenguajes y discutir qué cambió realmente: sintaxis, null safety, inferencia, colecciones, funciones o expresividad.

### Predice antes de ejecutar · 3–8 min
Antes de correr el programa, anticipar salida, valor de variables o efecto de una expresión Kotlin. Especialmente útil para `if` como expresión, `when`, null safety, lambdas, colecciones y corrutinas cuando correspondan.

### Bug de la semana · 5–10 min
Diagnosticar un error pequeño en Kotlin o Android. Deben explicar expectativa, comportamiento observado y causa.

### Forma explícita → forma idiomática · 10–15 min
Partir con ciclos/condiciones visibles y luego reconocer cuándo `filter`, `map`, `count`, lambdas u otras abstracciones comunican mejor la intención.

### Feature sorpresa PocketLog · 15–30 min
Agregar una necesidad pequeña al mismo software vivo usando únicamente herramientas habilitadas curricularmente.

Ejemplos futuros: nueva consulta, nueva validación, cambio de estado, nueva pantalla, persistencia, cámara o consumo REST cuando cada contenido corresponda.

### UI ugly → UI usable · 15–30 min
Cuando el curso entre a Android/Compose, entregar una pantalla funcional pero pobre y pedir mejoras de jerarquía, consistencia, accesibilidad o adaptación sin alterar la lógica de negocio.

### Refactor challenge · 10–20 min
Mejorar una sección funcional de PocketLog sin cambiar comportamiento. El refactor debe estar limitado a conceptos ya estudiados.

### Mini defensa · 2 min
Explicar una decisión: `val` vs `var`, nullable vs no nullable, función vs código repetido, `List` vs `MutableList`, ubicación de estado, responsabilidad de ViewModel, etc., según el momento del semestre.

### README destacado
Reconocer documentación particularmente útil y reproducible. Puede recibir compensación/bonificación cuando el docente lo determine.

### Commit arqueológico · 10–15 min
Comparar PocketLog actual con un checkpoint anterior y explicar qué necesidad provocó cada cambio.

### App del día real · 10 min
Observar una app conocida y analizar una sola dimensión vinculada al contenido actual: navegación, formularios, persistencia aparente, permisos, cámara, feedback visual, etc. No se intenta inferir toda su arquitectura.

### Boss fight · 30–60 min
Cada varias semanas, integrar varios contenidos recientes sobre PocketLog o un dominio distinto, sin introducir tecnología futura ni reemplazar una evaluación.

### Pregunta que una IA podría responder mal · 5–15 min
Revisar una respuesta o fragmento plausible y verificarlo ejecutando, contrastando documentación o razonando sobre el comportamiento.

## Rotación sugerida

```text
Fundamentos Kotlin → Predice / Java vs Kotlin duel
Colecciones       → Explícita → idiomática
POO Kotlin        → Refactor / Bug
Android inicial   → Mini defensa / App real
Compose/UI        → UI ugly → usable
Persistencia/REST → Bug / Feature sorpresa
Cierres de unidad → Boss fight / Commit arqueológico
```

## Criterio de éxito

La dinámica debe reforzar la comprensión y caber dentro del ritmo real de la clase. Si empieza a competir con PocketLog o exige demasiado material adicional, se simplifica.
