# Acompañamiento del proyecto VcM · DSY1105

## Caso

**Exploración móvil de innovación y capacidades I+D**  
Socio formador: **Centro UC de Innovación en Madera (CIM UC)**.

El caso corresponde a un problema real que los equipos deben analizar y resolver mediante un MVP académico. No existe una solución docente de referencia que los estudiantes deban replicar.

## Frontera de responsabilidad

El docente puede y debe:

- ayudar a comprender el contexto y detectar supuestos;
- cuestionar requerimientos y alcance;
- revisar coherencia entre problema, usuarios, datos, mockups y propuesta;
- canalizar dudas de negocio mediante **Estudiantes → Docente → CITT → Empresa/organización**;
- revisar trazabilidad, progreso y trabajo colaborativo;
- exigir que las decisiones sean justificables.

El docente **no debe diseñar ni implementar la solución del caso por los equipos**.

Los ejemplos, laboratorios y proyectos formativos del curso existen en dominios separados y enseñan técnicas transferibles. No constituyen una pauta del caso VcM.

## Inicio formal del proyecto

Antes de desarrollar código de forma significativa, cada equipo debe construir una base razonada:

```text
contexto
→ problema
→ usuario(s) priorizado(s)
→ requerimientos
→ alcance MVP
→ modelo de datos
→ mockups / flujo
→ propuesta de solución
```

No todos los artefactos deben estar cerrados desde el primer día. Sí deben tener suficiente consistencia para detectar problemas de interpretación y alcance antes de que resulten costosos.

## Preguntas que el equipo debe poder responder

- ¿Qué problema concreto intentamos resolver?
- ¿Para qué usuario o perfil?
- ¿Cuál es nuestro flujo principal?
- ¿Qué entra en el MVP?
- ¿Qué dejamos fuera y por qué?
- ¿Qué información necesita realmente la aplicación?
- ¿Cómo se relacionan esos datos?
- ¿Qué decisiones de UX o arquitectura estamos tomando?
- ¿Qué supuestos requieren validación externa?

## Restricciones del caso

- MVP académico, no producto definitivo.
- No reproducir íntegramente el sitio institucional.
- Usar datos ficticios, sintéticos, públicos o debidamente anonimizados.
- No utilizar credenciales, registros internos, datos personales no públicos ni infraestructura productiva.
- Representar integraciones mediante APIs de prueba, mocks, datos públicos o servicios simulados cuando corresponda.
- Priorizar un flujo principal completo antes que una colección extensa de funcionalidades.
- Los recursos nativos del dispositivo se incorporan **sólo cuando aportan al flujo elegido**, no como requisito artificial.
- El alcance debe ser viable para un equipo de máximo dos estudiantes.

## GitHub como evidencia del proceso

El repositorio debe mostrar construcción progresiva:

- commits reales y frecuentes;
- participación de ambos integrantes;
- cambios comprensibles;
- documentación de decisiones;
- evolución del producto, no una carga final monolítica.

La trazabilidad no reemplaza la defensa; la complementa.

## Relación con PocketLog

**PocketLog no resuelve el caso VcM.**

PocketLog es un proyecto formativo controlado para enseñar cómo evoluciona una aplicación cuando aparecen nuevas herramientas. El equipo debe transferir esos aprendizajes a su propio problema tomando nuevamente decisiones.

> Aprender una técnica no equivale a recibir una solución.
